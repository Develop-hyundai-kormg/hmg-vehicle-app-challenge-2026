# 공식 접수양식 02번 영역 초안 — 병원 동행 동선(C)

> **예비안 · 2026-11-09. 현재 1차 주력 추천에서 내렸고 제출 불가.** 앱명, 대상 병원 1곳, 실제 승하차·주차·픽업 지점, 최근 방문한 보호자 운전자의 응답, 4인 팀 정보와 혼합팀 참가 부문이 비어 있다. 이 초안을 공식 양식에 옮기기 전에 사용자 가치와 확장 비용을 다시 판단해야 한다. [최신 재판단](DIRECTION_REASSESSMENT_2026-11-09.md), [당시 근거와 실패 실험](INDEPENDENT_REVIEW_2026-11-09.md)

## 1. 앱 한 줄 소개

**초안:** 거동이 불편한 외래 환자를 모시는 보호자 운전자가 한 번의 병원 방문에서 **환자 하차 → 보호자 주차 → 환자 픽업**을 순정 내비 경로와 정차 후 확인 화면으로 이어 가는 차량용 앱입니다.

앱명은 미정이다. “안전한 하차 보장”, “무장애 경로 자동 추천”, “실시간 빈자리 안내”는 현재 근거가 없어 쓰지 않는다.

## 2. 기획 배경

**제출 전 보완할 문안:** 대상 병원 [이름]의 공식 안내에는 [검증한 방문 건물], [주차장], [주출입구]가 분리되어 있다. 최근 [확인한 날짜] 방문한 보호자 운전자 [익명 응답 수]명은 [실제 과거 행동과 불편을 인용 대신 요약]했다. 현재 쓰는 [병원 앱/지도 앱/전화 안내]의 절차와 비교하면 [확인된 빈틈]이 남는다. 앱은 한 방문에서 운전자가 입력하는 장소와 다음 행동을 연결해 이 빈틈을 줄이는지 검증한다.

**지금 쓸 수 있는 사실:** 공개 병원 안내에는 복수 주차장과 출입구가 있고, 일부 구역은 공사·혼잡 등으로 안내가 바뀐다. 이는 장소별 최신 검증이 필요하다는 근거이지 대상 보호자 모두가 길을 잃는다는 증거는 아니다. [서울대병원 주차 안내](https://www.snuh.org/content/E003007.do), [삼성서울병원 주차·위치 안내](https://www.samsunghospital.com/home/info/map.do).

**제출 전 필수:** 실제 보호자 운전자에게 최근 방문의 단계별 행동을 묻고, 같은 병원의 기존 앱/지도 앱이 이미 제공하는 기능을 직접 비교한다. 확인 전에는 문제의 빈도·시간 손실·앱 사용 의향을 숫자로 쓰지 않는다.

## 3. 앱 주요 기능 및 차량 특화 요소

1. 방문 전 **병원 공식 안내와 현장에서 확인한 세 장소**를 한 세트로 선택한다: 승하차 허용이 확인된 지점, 실제 주차장 입구, 픽업 지점. 화면에는 확인 날짜와 현장 표지를 우선하라는 안내를 둔다.
2. Pleos NaviHelper의 **경유지 경로 요청**으로 하차 지점을 거쳐 주차장으로 가는 순정 내비 경로를 연다. 공식 샘플에서 순정 내비 미리보기와 “경유지 1개 포함” 표시를 실행 확인했다. **우리 앱에서의 구현은 아직 미완료**다.
3. 정차 후 화면에서는 AAOS의 기어 상태와 CarUxRestrictions를 확인한다. 별도 검증 APK에서 P와 현재 제한 해제 상태를 읽었다. 환자가 내렸는지는 운전자가 직접 확인한다. Door SDK 값은 필요하면 보조 힌트로만 쓰며 안전 판단에 사용하지 않는다.
4. 주차 후 운전자가 픽업 요청을 받으면 검증된 픽업 지점으로 새 경로를 요청한다. 환자 휴대폰 알림, 병원 내부 길찾기, 주차장 실시간 잔여 면수는 초기 범위가 아니다.
5. 경로 요청 실패·차량 상태 불명·현장 안내 변경 시 앱은 위치나 안전을 추정하지 않고 병원 공식 안내와 현장 표지 확인을 요청한다.

차량에서의 가치는 장소 세 곳과 단계 전환을 **같은 방문 맥락, 순정 내비, 정차 상태**에 묶는 데 있다. 일반 지도에서 두 목적지를 직접 입력하는 절차보다 실제로 나은지는 현장 시험으로 확인해야 한다.

## 4. 주요 사용 시나리오

**검증 예정 시나리오:** [환자와 운전자 관계]가 [대상 병원·방문 건물] 외래 진료에 차로 간다. 출발 전 앱에서 방문 건물을 고르고, 앱이 제시한 하차·주차 장소가 병원의 현재 공식 안내와 맞는지 확인한다. 운전자가 “하차 후 주차”를 누르면 순정 내비에 경유지 포함 경로 미리보기가 열린다. 현장에 도착해 합법적으로 정차하고 환자를 보호 인계한 후, P 상태에서 운전자가 “하차 완료”를 누른다. 주차장으로 이동하고, 진료 후 환자의 연락을 받은 운전자가 픽업 지점을 확인해 경로를 연다. 위치나 차량 상태를 읽지 못하면 앱은 다음 단계를 자동 확정하지 않는다.

**현 상태:** 42dot 시험 POI로 경유지 경로 미리보기까지 실행했다. 병원 POI, 하차 후 경로 지속, 픽업 재경로, 주행 중 화면 제한, 실제 보호자 동선은 아직 시험하지 못했다. 시나리오를 완료된 제품 경험처럼 쓰지 않는다.

## 6. 기대효과 및 발전 가능성

첫 목표는 **한 방문에서 잘못된 입구 선택, 하차 후 다시 목적지 입력, 픽업 장소 재확인**에 드는 행동을 줄이는 것이다. 효과를 주장하려면 기존 방식과 자체 앱을 같은 병원 방문 과제로 비교해 단계 수, 수정 입력 수, 완료 시간, 잘못 진입한 횟수를 기록해야 한다. 의료 안전이나 보행 거리가 실제로 개선됐다는 수치는 현장 측정 전까지 쓰지 않는다.

초기 타깃은 Pleos 지원 차량으로 **거동 불편 환자의 외래 방문을 반복하는 보호자 운전자**다. 예상 MAU는 “해당 지역 Pleos 지원 차량의 대상 운전자 수 × 월간 해당 병원 방문 비율 × 설치·활성화 비율”로 계산하고, 각 입력값의 출처·불확실성을 함께 적는다. 지금은 분모가 확인되지 않아 숫자를 채우지 않는다. 재사용률은 첫 방문에 앱을 쓴 사람 중 다음 방문에도 다시 쓴 비율로 정의하며, 재방문 기회가 없는 사람은 별도로 구분한다.

한 병원에서 실제 이점이 확인되면 공식 안내와 현장에서 확인한 장소 데이터를 병원별로 추가할 수 있다. 확장할수록 주차·하차 정책과 출입구 변경을 지속 확인해야 한다. 병원과의 정보 협력이나 유료 사업 모델은 합의 전에는 계획 또는 가능성으로만 제시한다.

## 7. 선택 참고자료의 현 상태

- **가능한 기술 증거:** 공식 샘플의 경유지 경로 요청 결과와 별도 기어/UX 검증 앱 결과. 팀 자체 제품 시연 영상이 아니다.
- **현재 없음:** 팀 자체 앱 소스, release APK, 실제 병원 POI·현장 동선, 실사용자 시험 결과.
- **제출 조건:** 팀 자체 앱을 만들고 새 설치·경로 요청을 확인한 후 GitHub 소스와 실행 가능한 release APK를 함께 제출한다. 비공개 저장소의 심사용 계정 접근도 확인한다. [공식 제출 안내](https://appdevchallenge.auto-hmg.io/guide/submission)

### 4인 팀에게 필요한 최종 입력

대상 병원과 건물, 현장 확인 날짜·증거, 사용자 응답, 기존 앱 비교, 앱명, 대표자·팀원 역할, 혼합팀 참가 부문에 대한 운영사무국 답변, 각자 서명·날짜, 제출 링크 접근 확인. 이 정보와 앱 실행 결과가 들어오기 전에는 공식 양식에 사실처럼 복사하지 않는다.

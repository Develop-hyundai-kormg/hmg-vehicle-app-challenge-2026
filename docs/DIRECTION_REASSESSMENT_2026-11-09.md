# 2026-11-09 방향 재판단 — 병원안을 주력 추천에서 내림

> **현재 결론: 1차 주력 추천 후보 없음.** 병원 하차→주차→픽업(C)은 구현 실험 사례·예비 기획으로 보존한다. 이 판단은 팀원 보고서 3건, 데스크탑 Pleos 실행 결과, 2026-11-09 공식 심사 기준과 기존 제품 자료를 다시 비교한 결과다. 출품 포기나 다른 후보 확정을 뜻하지 않는다.

## 이전 판단에서 고친 점

이전 [독립 재검증](INDEPENDENT_REVIEW_2026-11-09.md)은 C를 **조건부 1순위**로 적었다. 경유지 경로 요청이 실제 실행됐고 병원 1곳이면 작은 시연이 가능하다는 점을 높게 봤다. 그러나 [공식 1차 필수 평가](https://appdevchallenge.auto-hmg.io/guide/judging-awards)는 차량특화성·창의성·SDK 활용·사업성을 모두 본다. 실행 영상과 소스·APK는 **선택 가산점**이고, 기획서만으로도 접수할 수 있다. 따라서 작은 시연의 쉬움을 제품 가치·1차 경쟁력의 우위로 옮겨 적은 것은 판단 오류였다. [공식 제출 안내](https://appdevchallenge.auto-hmg.io/guide/submission)

**한 병원으로 시작하는 MVP 자체가 문제인 것은 아니다.** 한 병원에서 확인한 장소 데이터를 다른 병원으로 늘릴 때마다 승하차 정책·출입구·주차 진입로·픽업 지점의 정확성과 갱신 책임이 따른다. 반복 동행 운전자라는 고객군의 규모·월 사용 빈도·시간 절약도 아직 측정하지 않았다. 일반 지도 경유지와 병원 길찾기 앱보다 나은 행동 결과가 없으면 차량 앱이어야 할 이유가 약하다. [Johns Hopkins 병원 길찾기](https://www.hopkinsmedicine.org/patient-care/locations/find-your-way), [ChocoTracks의 주차 위치·길찾기](https://choc.org/chocotracks/)

팀원 보고서도 C를 합격 가능한 최선이라고 입증하지 않았다. C 추천 보고서는 **추가 검증 후 결정**을 결론으로 적고 병원 데이터·낮은 재사용률을 반대 근거로 명시했다. 운행기록 보고서는 오히려 **운행기록 > C**로 검증 순서를 제안했다. 공용차 보고서는 인계의 반복성에 주목했지만 연료 API·실제 조직 문제를 미확인으로 표시했다. 세 보고서의 공통 결론은 ‘주력 확정 전 사용자·기술 확인’이다.

## 데스크탑 추가 시험: 차량값 주입의 제한

2026-11-09 Windows 데스크탑에서 Pleos Connect v2.1.0 전용 AVD를 헤드리스 SwiftShader로 콜드 부팅하고 별도 진단 APK를 다시 실행해 기어 `4`(P), `CarUxRestrictions active=0`, AAOS 직접 누적거리 `CAR_MILEAGE` 권한 오류를 재현했다. Android [공식 가상 주행 시험](https://source.android.com/docs/automotive/driver_distraction/consume)에 나온 `dumpsys activity service com.android.car inject-vhal-event`는 이 이미지에서 차량 상태를 바꾸지 않았다. 별도 `adb shell cmd car_service inject-vhal-event 0x11400400 8`은 **`SecurityException: ... requires non-user build`**로 거절됐다. `ro.build.type=user`를 확인했다. 기존 Virtual Console의 503 `emulator_inactive`와 별개인 시험 결과다. 차량 신호를 바꾸는 지원된 다른 경로가 전혀 없다는 뜻은 아니며, **현재 재현한 경로로는 변화 콜백을 증명하지 못했다**는 뜻이다. ## 1차 주제를 정할 때 필요한 증거

1. **실제 반복 불편:** 최근 사용 사례를 먼저 듣고, 지금 쓰는 앱·순정 기능·메신저가 어떻게 해결하는지 같은 과제로 비교한다. ‘쓰고 싶다’는 의견만으로 수요를 확정하지 않는다.
2. **차량 안에서만 생기는 이점:** 차량 데이터가 어떤 결정을 바꾸는지, 일반 휴대폰 화면·내비 즐겨찾기로 같은 일을 할 수 없는지 확인한다. SDK를 호출했다는 사실만으로 차량특화성을 주장하지 않는다.
3. **12월까지 작동할 핵심 한 장면:** 공식 Pleos 환경에서 값 또는 경로가 실제로 앱에 전달되고, 실패할 때도 안전하게 동작해야 한다. 목업과 공식 샘플은 제품 구현으로 세지 않는다.
4. **확장 비용과 재사용:** 최초 시나리오를 넘어 데이터·권한·운영 인력이 얼마나 더 필요한지 적고, 실제 재사용 기회를 정의한다.

**짧은 병렬 검증 제안(11월 10~11일 팀 내부 결정 목표):** 업무용 차 운전자/관리자와 작은 공용차 운영팀의 최근 사례를 각각 확인하고, 카택스·Pleos Fleet·기아 비즈의 같은 과제 화면과 대조한다. A는 목표 Pleos 차량에서 목적지 없이 순정 경고가 나오는지와 카메라 전용 앱 정책을 별도 확인한다. C는 병원 현장·보호자 검증에서 예상을 뒤집는 강한 결과가 있을 때만 재검토한다. **사용자 인터뷰·현장 방문·운영사 문의는 아직 수행하지 않았다.**

## 제출 문안에 미치는 영향

# 1차 제출안 준비표

기준일: **2026-11-08**. 주제 선택과 구현 결과가 없으므로 아래는 **작성·검증 순서**다. 현재 제출 완료를 뜻하지 않는다.

## 먼저 결정할 것

1. 팀원의 독립 검토에서 사용자 문제와 기존 서비스의 빈틈이 남는 후보를 고른다.
2. 그 후보의 핵심 Pleos 데이터·권한·정책을 가장 작은 에뮬레이터 시험으로 확인한다.
3. 1차에 실제 앱으로 보일 수 있는 범위와 목업/추후 개발 범위를 구분한다.
4. **2차 실제 앱 시연**까지 개발할 사람·시간·환경이 있는지 확인한다.

기술/사용자 가치 관문을 넘은 후보가 없다면 억지로 주력안을 정하지 않는다. 공식 규정상 기획서만으로 1차 접수는 가능하지만, 합격 후 12월 3~4일 앱 시연 의무가 있다. [공식 심사·시상](https://appdevchallenge.auto-hmg.io/guide/judging-awards)

## 공식 DOCX의 1~6번을 채우는 방법

| 항목 | 넣을 정보 | 피할 주장 |
|---|---|
| 1. 한 줄 소개 | 대상 사용자 + 차량 안의 불편 + 바꾸는 결과를 한 문장으로 | 기능을 여러 개 나열한 구호 |
| 2. 기획 배경 | 최근 실제 사례, 기존 앱이 남기는 빈틈, 대상 집단. 확인하지 못한 사용자 반응은 가설 표시 | 커뮤니티 글 몇 개를 발생률이나 수요 규모로 일반화 |
| 3. 기능·차량 특화 | 한 번의 핵심 흐름과 그때 쓰는 차량 신호/API, 모바일만으로 어려운 이유 | 차로 인식·앞차 거리·법규 판정을 공개 신호만으로 자동화했다고 표현 |
| 4. 사용 시나리오 | 누가 언제 앱을 켜고, 주행 중 무엇이 나오고, 주차 후 무엇을 결정하는지. 자동 시작이 미확인이면 미확인 표기 | 수동 실행 시연을 자동 실행 경험으로 서술 |
| 5. 개발 계획 | SDK 버전/권한/차종 capability, 검증된 기능, 미확인 관문, 2차까지의 작업 순서와 실패 시 범위 | SDK 인터페이스 존재를 실행 완료로 표현 |
| 6. 기대효과·사업성 | 타깃, 사용 빈도 가설, 기존 대안 대비 재사용 이유, MAU·유지율 계산 가정 | 실사용자가 없는 현재 시점의 임의 실적·합격 확률 |

MAU는 예를 들어 `접근 가능한 Pleos 탑재 차량 운전자 × 설치율 × 월간 재사용률`처럼 **모집단과 가정**을 공개하고 추정한다. 다음 달 유지율은 `첫 달 사용자 중 다음 달에도 사용한 비율`로 정의한다. 실제 사용자 테스트가 없다면 `실측`이라고 쓰지 않는다.

## 선택 제출물

- **영상:** 목업·프로토타입·화면 녹화가 인정된다. 영상 장면마다 `실제 앱 실행` 또는 `화면 시안/목업`을 명확히 적는다. 실제 앱을 보여줄 수 있다면 `차량 신호/내비 이벤트 → 앱 반응 → 사용자 결과`가 이어진 한 장면을 우선한다. 시뮬레이터 입력은 시뮬레이션이라고 표시한다.
- **GitHub + APK:** 소스와 실행 가능한 **release APK를 `apk/` 경로에 함께** 둔다. README에는 실행법, 환경, 설정과 APK 경로를 쓴다. APK가 없으면 저장소를 개발 완료 증거처럼 제출하지 않는다. 비공개 저장소를 심사 자료로 제출할 경우, 공식 안내의 심사용 GitHub 계정이 접근 가능한지 마감 전 확인한다. [GitHub 제출 안내](https://appdevchallenge.auto-hmg.io/guide/submission)
- **시안:** 실제 제품 경험과 기술 관문을 드러내는 최소 화면을 만든다. 주차 후 체크리스트라면 관측 사실, 운전자 확인/정정, 상세의 세 화면 안에서 시작한다. 카메라 경고라면 내비 미사용/사용 중 중복 억제 상태를 보여주되, 기술 검증 전에는 목업이라고 표시한다.

가산점의 크기·합격 확률은 공개되지 않았다. 영상이나 코드를 첨부하더라도 네 가지 필수 평가항목을 설명하는 기획서가 중심이다. [공식 심사 기준](https://appdevchallenge.auto-hmg.io/guide/judging-awards)
